# CLAUDE.md — Accounting Telegram Bot

This file is the source of truth for the project. Read it fully before writing code, and re-read the **Non-negotiables** section before any change that touches numbers, classification, or aggregation.

## What we are building

A Telegram bot that turns a bank statement into a **cash-basis income statement**, plus an agentic Q&A interface over the same transactions.

A user sends a bank statement file (XLSX/CSV) into the Telegram chat. The bot parses it, classifies each transaction, stores everything, and replies with a categorized income statement. The user can then ask free-text questions ("how much did I spend on food in March?") and get answers that cite the exact source transactions.

**Demo data:** a synthetic English bank statement, generated by `scripts/generate_data.py` in Revolut export layout and committed under `data/`. Built so a real Revolut export can be dropped in later with no parser changes. Generation also emits a draft ground-truth label file (`eval/labels.csv`) that a human reviews — generated labels used unreviewed would make the accuracy eval circular.

## Honest accounting — labeling rules (do not violate)

- A bank statement records **cash movement only**. The legitimate output is a **cash-basis income statement** (a.k.a. cash-basis P&L / financial summary). Label it exactly that in all user-facing text and in the README.
- **Never** call the output a "Statement of Financial Position" or "Balance Sheet" — a bank statement contains no asset/liability/equity data, so those are impossible to produce here. Producing them would be an accounting error.
- Do not imply accrual accounting. We do not match invoices to payments; we only categorize cash flows.

## Multilingual posture (English demo, multilingual-ready)

The project's purpose is the Central Asian market (Russian / Kyrgyz / English documents). The demo runs on English, but the build stays multilingual-ready:
- Embedding model is multilingual (see Stack).
- The classification prompt is written language-agnostically — it must work on Russian and Kyrgyz descriptions without code changes, only by feeding different input.
- README states: designed for RU/KY/EN, demoed on English Revolut data.

## Stack

- Python 3.11+
- `python-telegram-bot` (current stable, v21+), **polling mode** for the demo (no webhook, no public server needed)
- `pandas` + `openpyxl` for reading XLSX/CSV (deterministic number handling)
- `langgraph` for the pipeline graph and the Q&A subgraph
- `langchain` for the LLM interface and tool definitions
- `chromadb` (local / in-process, no server)
- `sentence-transformers` with **`paraphrase-multilingual-MiniLM-L12-v2`** for embeddings (local, no API key, works on EN/RU/KY)
- `sqlite3` (standard library) — the structured store and source of truth
- LLM for classification + Q&A reasoning: a hosted chat model behind a single `get_llm()` factory in one module, so it is swappable. Default to whichever API key is present in `.env` (Anthropic or OpenAI). **Temperature 0** everywhere — this tool must be reproducible.

Secrets in `.env` (never commit): `TELEGRAM_BOT_TOKEN`, and one of `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`.

## Architecture (the one diagram that matters)

```
Bank statement (XLSX/CSV)
        │  parse  (pandas — DETERMINISTIC, numbers never touch the LLM)
        ▼
  Canonical transactions
        │  classify (LLM reads DESCRIPTION TEXT ONLY, cached, temp 0)
        ▼
   SQLite store  ◄──────────────── SOURCE OF TRUTH
        ├─ aggregate (deterministic sum over ALL rows) ─► Income statement  → /statement
        └─ Q&A agent ─► answers                                            → free-text messages
              ├─ sql_query tool   (numeric questions — exact, complete)
              ├─ vector_search    (Chroma — ONLY for fuzzy/semantic questions)
              └─ filter tool      (date / vendor / category)
```

## Data model

SQLite table `transactions`:

| column        | type    | notes                                                            |
|---------------|---------|-----------------------------------------------------------------|
| id            | INTEGER | primary key                                                     |
| date          | TEXT    | ISO `YYYY-MM-DD`                                                 |
| description   | TEXT    | raw description/memo from the statement                         |
| amount        | REAL    | **signed**: positive = inflow, negative = outflow               |
| currency      | TEXT    |                                                                 |
| category      | TEXT    | one of: `revenue`, `expense`, `excluded`                        |
| subcategory   | TEXT    | see taxonomy                                                    |
| confidence    | REAL    | 0–1 from the classifier                                         |
| justification | TEXT    | short LLM reason — the audit trail                              |
| source_ref    | TEXT    | source file name + original row index                          |

Plus a `classification_cache` table keyed by **normalized description** → (subcategory, category, confidence, justification), so each distinct description is classified once.

## Taxonomy (three top-level buckets — this is mandatory)

- **revenue** — operating income / sales received
- **expense** — `cogs`, `rent`, `salaries`, `utilities`, `supplies`, `fees`, `taxes`, `other_opex`
- **excluded** — `transfer`, `loan_in`, `loan_out`, `owner_draw`, `owner_contribution`, `capital_purchase`, `refund`

The **excluded** bucket is the whole point of correctness: a loan received is NOT revenue, a transfer to savings is NOT an expense, buying equipment is NOT an operating expense. Excluded items are shown to the user as a separate total but are **kept out of the net-income calculation**.

Net income (cash basis) = total revenue − total expense. The excluded bucket never enters this line.

## Pipeline (LangGraph)

Nodes, in order: `parse → classify → store → aggregate → validate`.

- **parse** — pandas reads the file, normalizes columns (date, description, signed amount, currency) into canonical transactions. Different banks use different column layouts; for the demo, support the Revolut export layout and keep the column mapping in one config dict so other banks can be added later. **No LLM in this node.**
- **classify** — for each *distinct* normalized description: check `classification_cache`; on miss, call the LLM with description text only, get `{category, subcategory, confidence, justification}`, write to cache. The LLM never sees or returns amounts.
- **store** — write classified transactions to SQLite; embed each description into Chroma with the transaction id as metadata.
- **aggregate** — pure SQL/pandas. Group by category/subcategory, sum, compute net income. Iterates the **complete** set of rows — never via vector retrieval.
- **validate** — checks below.

## Validation node (run before returning any statement)

- Every transaction has a non-null category.
- Sum of categorized amounts reconciles to the sum of all P&L-relevant rows (no row silently dropped).
- No duplicate rows (same date + amount + description) double-counted.
- Flag transactions with confidence below a threshold (e.g. 0.6) for user review.
- Flag any single transaction that is an outlier share of its category.

The statement returned to the user notes how many rows (if any) are low-confidence.

## Q&A agent (separate LangGraph subgraph — NOT a single RetrievalQA chain)

Tools the LLM can choose between:
- `sql_query(question)` — for any numeric/aggregate question. Translates to SQL over the store. **This is the default for anything involving a number.** Exact and complete.
- `vector_search(query)` — Chroma similarity search over descriptions. Use ONLY for fuzzy/semantic lookups where the relevant transaction isn't identified by an exact filter.
- `filter(date_range?, vendor?, category?)` — structured filtering over the store.

Every answer must cite the source transaction id(s) it used. If the agent can't answer from the data, it says so — it does not invent figures.

## Telegram handlers

- **Document message (XLSX/CSV)** — download the file, run the pipeline, reply with a short summary (rows processed, any low-confidence flags) and the income statement.
- **`/statement`** — re-send the current income statement, formatted.
- **`/reset`** — clear the store and cache so the demo can be re-run cleanly.
- **`/start` / `/help`** — short usage text.
- **Any other text** — route to the Q&A agent; reply with the answer + cited transaction ids.

Format the income statement as readable Telegram message text (monospace block for the numbers). Keep it under Telegram's message length limit; if long, send the statement as a generated `.txt`/`.csv` file.

## Non-negotiables (re-read before touching numbers)

1. **Amounts are parsed deterministically and never produced by the LLM.** The LLM only ever reads description text to assign a category. A misread amount disqualifies the tool.
2. **Classification is cached by normalized description and runs at temperature 0.** The same statement classified twice must give identical totals.
3. **The three-bucket taxonomy is mandatory.** `excluded` items (transfers, loans, owner draws, capital, refunds) are kept out of net income.
4. **SQLite is the source of truth. Aggregation iterates every row.** Never compute a statement total from vector retrieval — vector search returns top-k by similarity and will silently drop rows.
5. **Vector search is used only in Q&A, only for semantic questions.** Numeric questions go through `sql_query`.
6. **Everything is auditable.** Each classification stores a justification + source_ref; each Q&A answer cites transaction ids.
7. **Honest labeling.** Cash-basis income statement / financial summary. Never SFP / balance sheet.

## Testing & eval (do not skip)

- `eval/test_classification.py` — compares the classifier against `eval/labels.csv` (the human-reviewed ground truth seeded in Phase 0) and prints accuracy.
- `eval/test_qa.py` — runs `eval/qa_pairs.yaml` (8–10 Q/A pairs) through the agent and prints a pass rate.
- README reports both numbers and the honest scope/limitations (cash-basis only, single bank layout, XLSX/CSV only, in-person-pickup banks noted as real-world friction).
